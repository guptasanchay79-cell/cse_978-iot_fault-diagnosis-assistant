# Database Persistence Layer Documentation

## 1. Overview & Architectural Role

In the **P_311: Knowledge-Driven IoT Fault Diagnosis Assistant**, the database serves as a **persistence layer only**. 

The core diagnostic pipeline functions independently:
```
Simulator (1 Hz) ──> MQTT (Mosquitto) ──> Fault Detector ──> RAG Retriever ──> Local LLM (Ollama) ──> Dashboard SSE
                           │                                                          │
                           ▼                                                          ▼
             telemetry_readings (PostgreSQL)                             fault_incidents (PostgreSQL)
```

### Architectural Principles
- **Decoupled Persistence**: The real-time streaming pipeline never blocks for database I/O. If PostgreSQL is stopped, restarting, or unavailable, the assistant continues operating with in-memory state and local JSONL logging (`data/diagnoses_log.jsonl`).
- **Persistence Layer Only**: The database persists historical sensor readings and fault diagnoses across application restarts. It does not replace the messaging layer (MQTT) or the in-memory telemetry buffer used by the web UI charts.
- **Circuit Breaker Pattern**: The application detects database connectivity with a 2-second timeout and caches failure status for 5 seconds. If PostgreSQL is offline, HTTP requests and the 1 Hz telemetry loop experience zero lag.

## 2. Windows Native PostgreSQL Service Deployment

The persistence layer runs directly on Windows as a local service (`postgresql-x64-18`).

### Connection Configuration
All connection settings are loaded dynamically from environment variables or the `.env` file (git-ignored):
- `POSTGRES_HOST=127.0.0.1`
- `POSTGRES_PORT=5432`
- `POSTGRES_USER=postgres`
- `POSTGRES_DB=p311_iot_diagnostics`
- `POSTGRES_PASSWORD=<configured_in_.env>`

### Automated Database Initialization (`scripts/init_db.py`)
Running `python scripts/init_db.py`:
1. Connects to the local PostgreSQL server on Windows.
2. Creates the target database (`p311_iot_diagnostics`) if it does not already exist.
3. Applies `db/init.sql` to generate tables, indexes, constraints, and the retention pruning procedure.

## 3. Database Schema Reference

The database uses standard plain tables without partitioning. Floating-point sensor measurements and latencies use `DOUBLE PRECISION` for numerical fidelity.

### 3.1 `fault_incidents` Table
Stores diagnoses generated by the RAG + LLM inference pipeline.

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | Auto-incrementing identifier |
| `timestamp` | `TIMESTAMPTZ` | `NOT NULL` | Time of reading that triggered detection |
| `device_id` | `VARCHAR(64)` | `NOT NULL` | Device identifier (e.g., `pump_centrifugal_01`) |
| `fault_category` | `VARCHAR(64)` | `NOT NULL` | Classification (e.g., `bearing_wear`, `overheating`) |
| `symptoms` | `JSONB` | `NOT NULL DEFAULT '[]'` | Specific sensor thresholds violated |
| `temperature` | `DOUBLE PRECISION` | | Temperature reading (°C) at fault trigger |
| `vibration` | `DOUBLE PRECISION` | | Vibration reading (mm/s RMS) at fault trigger |
| `pressure` | `DOUBLE PRECISION` | | Discharge pressure reading (bar) at fault trigger |
| `retrieved_sources` | `JSONB` | `NOT NULL DEFAULT '[]'` | Technical manuals retrieved by RAG with scores |
| `diagnosis_text` | `TEXT` | | Complete structured diagnostic text from LLM |
| `likely_fault` | `TEXT` | | Top root cause identified |
| `why` | `TEXT` | | Evidence and physical justification |
| `recommended_checks` | `TEXT` | | Actionable maintenance procedures |
| `confidence_limitations` | `TEXT` | | Grounding confidence and constraints |
| `sections` | `JSONB` | `NOT NULL DEFAULT '{}'` | Parsed dictionary of all report sections |
| `runtime` | `VARCHAR(64)` | | LLM execution model (`ollama` or `grounded_synthesis_fallback`) |
| `latency_seconds` | `DOUBLE PRECISION` | | Time taken for RAG retrieval and inference |
| `created_at` | `TIMESTAMPTZ` | `DEFAULT CURRENT_TIMESTAMP` | Row creation timestamp |

**Indexes & Constraints**:
- `CONSTRAINT uq_fault_incident_device_ts UNIQUE (device_id, timestamp)`: Guarantees idempotent imports from JSONL logs.
- `CREATE INDEX idx_fault_incidents_timestamp ON fault_incidents (timestamp DESC);`
- `CREATE INDEX idx_fault_incidents_device_timestamp ON fault_incidents (device_id, timestamp DESC);`
- `CREATE INDEX idx_fault_incidents_category ON fault_incidents (fault_category);`

### 3.2 `telemetry_readings` Table
Stores raw 1 Hz sensor readings ingested from the MQTT telemetry stream.

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | Auto-incrementing identifier |
| `timestamp` | `TIMESTAMPTZ` | `NOT NULL` | Sensor sample timestamp |
| `device_id` | `VARCHAR(64)` | `NOT NULL` | Monitored equipment ID |
| `temperature` | `DOUBLE PRECISION` | `NOT NULL` | Motor bearing temperature (°C) |
| `vibration` | `DOUBLE PRECISION` | `NOT NULL` | Radial vibration velocity RMS (mm/s) |
| `pressure` | `DOUBLE PRECISION` | `NOT NULL` | Pump discharge pressure (bar) |
| `mode` | `VARCHAR(32)` | `NOT NULL DEFAULT 'normal'` | Operating state at sampling time |
| `created_at` | `TIMESTAMPTZ` | `DEFAULT CURRENT_TIMESTAMP` | Ingestion timestamp |

**Indexes**:
- `CREATE INDEX idx_telemetry_timestamp ON telemetry_readings (timestamp DESC);`
- `CREATE INDEX idx_telemetry_device_timestamp ON telemetry_readings (device_id, timestamp DESC);`

## 4. Telemetry Ingestion & Retention Lifecycle

### 4.1 Non-Blocking Telemetry Ingestion
Sensor telemetry streams at 1 Hz from `telemetry_producer()`. To prevent database latency from stalling the 1 Hz stream:
1. `telemetry_producer()` enqueues readings using `telemetry_queue.put_nowait(reading)`.
2. If `telemetry_queue` reaches capacity (`maxsize=1000`), a `queue.Full` exception is caught, and the oldest unwritten reading is dropped with a log warning.
3. The 1 Hz sensor generation and MQTT publish loop never blocks.

### 4.2 Batch Writer Thread
A dedicated background thread (`telemetry_db_writer_worker`) pulls readings from `telemetry_queue` and writes them in batches:
- Batches are flushed when buffer reaches `TELEMETRY_BATCH_SIZE` (20 readings) or when `TELEMETRY_BATCH_FLUSH_INTERVAL` (2.0 seconds) has elapsed.
- Writes use `cur.executemany(...)` via `psycopg` to minimize roundtrips.

### 4.3 Retention Pruning (`prune_old_telemetry()`)
To prevent unbounded storage growth of continuous 1 Hz telemetry:
- **Who calls it?** The background `telemetry_db_writer_worker` thread.
- **When is it called?**
  1. Once at application startup when `telemetry_db_writer_worker` initializes.
  2. Periodically once per hour (`prune_interval = 3600.0` seconds) during normal runtime.
- **What does it do?** Executes `SELECT prune_old_telemetry(retention_days)` (default: 7 days), deleting telemetry records with timestamps older than `CURRENT_TIMESTAMP - 7 days`. Diagnoses in `fault_incidents` are preserved indefinitely.

## 6. Viva / Examination Questions & Answers

### Q1: Why use a relational database (PostgreSQL) instead of purely persisting to JSONL files?
**Answer**: JSONL files append quickly but cannot be indexed, queried with range filters, or joined. As logs grow to thousands of records, searching or paginating requires reading and deserializing the entire file into memory. PostgreSQL provides B-tree indexing on timestamps and fault categories, atomic transactions, and concurrent read/write isolation between the streaming telemetry thread and HTTP API queries.

### Q2: Why is the telemetry insertion decoupled using a queue and background thread?
**Answer**: The physical telemetry simulator runs on a rigid 1 Hz clock cycle to simulate continuous industrial sensor sampling. If database insertion were synchronous, any network hiccup, disk I/O stall, or connection renegotiation would block the thread, causing telemetry jitter and delayed MQTT message delivery. Using a non-blocking queue (`put_nowait()`) with batch inserts completely isolates the real-time sensor loop from storage latency.

### Q3: What happens to the system if PostgreSQL service stops during operation?
**Answer**: The assistant implements graceful degradation with a circuit breaker. `is_database_available()` catches connection failures within a 2-second timeout and caches the offline state for 5 seconds. The dashboard continues serving live data from in-memory buffers, publishes via MQTT, and writes diagnoses to `data/diagnoses_log.jsonl`. When PostgreSQL recovers, subsequent checks reconnect automatically without restarting the application.

### Q4: Why use `DOUBLE PRECISION` instead of `REAL` or `FLOAT` for sensor measurements?
**Answer**: In PostgreSQL, `REAL` is a 4-byte single-precision float (approximately 6 decimal digits of precision), while `DOUBLE PRECISION` is an 8-byte IEEE 754 floating-point type matching Python's native `float` (15-17 decimal digits). Using `DOUBLE PRECISION` prevents precision loss or rounding artifacts when storing physical sensor values, noise drift calculations, and sub-millisecond inference latencies.

### Q5: How does the system handle storage growth from continuous 1 Hz sensor streams?
**Answer**: 1 Hz streaming generates 86,400 readings per sensor per day. To prevent disk exhaustion, the persistence layer defines a 7-day retention policy executed by `prune_old_telemetry()`. This pruning routine is invoked at startup and once every hour by the background writer thread. Diagnoses in `fault_incidents` are kept indefinitely because fault occurrences are relatively sparse and carry high technical value.
